## Pick up here: #872 — captured payment, cancelled order, money kept

**This is the priority and it is a live money bug, not a stuck screen.**

Verified today in the app: order `#SAFFRON-HOME-KITCHEN-HC26073113579923` (₹603.30,
31 Jul 11:57pm) shows **Cancelled**, price breakdown ends at Total with **no
`Refunded` line**, and no cancellation banner. A genuinely refunded order on the
same account (₹272.58) shows a green `Refunded −₹272.58` plus a "refunded to your
original payment method" banner. This one has neither.

**Root cause chain:**

1. Cashfree captures the money.
2. `settleCashfreeOrder` (`apps/api/handlers/payment_cashfree.go:330-345`) treats an
   upstream fetch error identically to "payment not completed" → HTTP 400. The
   client can't tell a retryable error from a terminal one, and stops polling
   (compounded by the auth token expiring → 401).
3. 30 min later `apps/api/services/stale_order_cron.go` cancels the order and
   stamps `payment_status = failed`. It makes **no gateway call** — the comment
   literally reads `// Mark cancelled (no payment was captured, so nothing to refund)`,
   inferring capture state from our own DB row, which is the field that's wrong
   in this failure mode.
4. Nothing refunds. Customer is told nothing.

**Webhooks are not configured** — `POST /webhooks/cashfree` is routed
(`routes.go:223`) but had 0 hits in 24h, so client-side verify polling is the only
settlement path.

**Proposed fix, in risk order:**

1. **Stop the bleeding** — stale-order must ask the gateway before cancelling.
   Captured → settle, don't cancel. Captured-but-unwanted → refund, don't just
   stamp failed.
2. **Order reconcile cron** — model directly on
   `apps/api/services/meal_plan_advance_reconcile_cron.go`, which already solves
   this exact shape for tiffin advances ("captured advance whose client verify AND
   webhook were both lost"). The absence of an order-level equivalent *is* the gap.
   Register in `cron_temporal.go`'s `cronJobs()`.
3. **Fix the error signal** — 502 for upstream failure vs 400 for genuinely unpaid.
4. Webhook configuration — ops task, not code.

**Open decision (unanswered):** do the code fix first, or first scope an audit
query to find historical orders already in this state (captured, cancelled,
unrefunded)? Real customers may be out of pocket. The audit needs prod DB access.
