# Phase gateway-fee-levy Plan 01: Vendor gateway-fee levy Summary

GH #885: Cashfree's per-refund transaction fee is now recovered from the chef through a
second `ChefPenalty` kind (`gateway_fee`), raised at a configured flat rate of the refunded
amount on every chef-fault Cashfree refund — CancelOrder, CancelOrderItem, RefundOrder, and
InitiateRefund's chef-initiated Cashfree branch — reusing the existing cancel_late
mechanism (raise → grace → waiver → weekly-statement deduction) unmodified.

## What Was Built

**Task 1 — Core mechanism** (`ca90412f`): `models.ChefPenaltyGatewayFee` kind constant;
`PlatformPolicy.GatewayFeeLevy*` fields (Enabled/Percent/GraceEnabled/GraceCount/GraceDays/
StackWithCancelLevy) with presence-aware pointer decode, defaulting OFF; `services.
GatewayFeeSourceKey`, `GatewayFeeLevyPolicy`, `LevyGatewayFeePenalty` — mirrors
`LevyChefCancelPenalty`'s shape (idempotency check first, then the stacking guard against an
existing cancel_late row on the same order, then the off-by-default grace guard, then the
pending-row create with duplicate-key tolerance); `CashfreeRefund.RefundChargePaise` parses
Cashfree's `refund_charge` field for observability only (never read by the levy arithmetic).

**Task 2 — Chef cancel/goodwill wiring** (`15b22de3`): best-effort `LevyGatewayFeePenalty`
calls added to `CancelOrder` (basis = the card-bound refund via `services.FromPaise(cardPaise)`,
keyed by `RefundFullIdempotencyKey`), `CancelOrderItem` (basis = `reservedRefund`, keyed by
`RefundLineIdempotencyKey`), and `RefundOrder` (basis = `reserved`, keyed by
`RefundPartialIdempotencyKey(order.ID, ToPaise(priorRefunded))`, fired regardless of whether
the order's own persist succeeded since the gateway refund already happened by that point).
Every call site logs + calls `services.CaptureBackgroundError` on failure and never touches
the refund/cancel response.

**Task 3 — InitiateRefund wiring** (`2cc630ed`): a best-effort, `initiatedBy == "chef"`-gated
call added after `crossGuardRefundHold` and before the final `c.JSON` response in
`InitiateRefund`. `refundAmount` is read there — after the wallet-at-checkout capping logic
has already possibly lowered it — so the levy basis is exactly the amount sent to Cashfree,
not the raw requested amount.

## Deviations from Plan

### Auto-fixed / Clarified Issues

**1. [Rule 4-adjacent clarification, not architectural] Call-site placement in payment.go**
- **Found during:** Task 3
- **Issue:** The plan's action text for Task 3 says to add the levy call "inside the
  `case models.PaymentProviderCashfree:` branch... immediately after `refundID = r.RefundID`"
  but in the same sentence also says "at the same point right before the final `c.JSON(...)`
  response" — the persist transaction and `crossGuardRefundHold` call happen AFTER the
  switch statement closes, for every provider, so these two locations are mutually
  exclusive in the actual code.
- **Resolution:** Followed the more specific, unambiguous instruction (placement right
  before the final `c.JSON`, after persist + crossGuard) and kept the guard explicit
  (`provider == models.PaymentProviderCashfree && initiatedBy == "chef"`) since the code is
  no longer syntactically inside the switch case at that point. This changes nothing about
  behavior or scope — every must-have in the plan (Cashfree-only, chef-initiated-only, basis
  = capped `refundAmount`, best-effort, no effect on the customer's refund) is preserved
  exactly.
- **Files modified:** apps/api/handlers/payment.go
- **Commit:** 2cc630ed

**2. [Implementation detail] Test policy-installation seam**
- **Found during:** Task 2/3 test-writing
- **Issue:** The plan didn't specify how handler-package tests should install the
  gateway-fee policy (the services package's `withPlatformPolicy` test helper that writes
  the process cache directly is unexported and unavailable outside `package services`).
- **Resolution:** Added `withGatewayFeeLevyEnabled` in the handlers test package that goes
  through the exported `services.SavePlatformPolicy` + `services.InvalidatePlatformPolicy`
  seam (the same path an admin write uses), backed by the `platform_settings` table already
  present in `setupPayDB`. No production code path affected.
- **Files modified:** apps/api/handlers/chef_order_cancel_gateway_fee_test.go (test-only)

No other deviations — the customer refund arithmetic (`InitiateRefund`, `CancelOrder`,
`CancelOrderItem`, `RefundOrder`) was not touched anywhere; every pre-existing refund/cancel
test passes unmodified.
