# Quick Task 260801-b19: Register FCM device tokens so push actually delivers

Closes tesserix/Home-Chef-App#870.

## Goal

`packages/mobile-shared/src/hooks/usePushToken.ts` blocks token registration
on every simulator (including Android emulators, which CAN receive FCM), and
`apps/mobile-{customer,vendor,delivery}/app/_layout.tsx` has three defects
that turn one failed `registerDeviceToken` call into total notification
silence for the session: no `try/catch` around the initial call (it aborts
everything after it), listener setup runs *after* that unguarded call, and
there's no retry path for a user who denies the permission prompt and later
enables it in Settings. Fix the guard, make every silent exit observable, and
make registration failures non-fatal to listener setup and self-healing on
foreground.

**Caveat to carry forward, not to resolve here:** the production log evidence
in #870 may itself be an artifact of the too-broad guard — a QA Android
emulator pointed at production can never register a token under the current
code, which alone would produce the exact "no FCM token" log lines cited.
Whether real hardware also fails is unconfirmed and needs
`select count(*) from users where fcm_token is not null and fcm_token <> ''`
against production, which is owner-gated DB access — not part of this plan.
This change is correct and needed regardless of that number: it fixes a
real over-broad guard, removes multiple silent failure modes, and makes push
testable on the emulator for the first time. Do not describe it as "confirmed
root cause of the production reports" until that query is run.

## Design decisions locked by this plan

**Guard narrowing.** `Device.isDevice` stays the base check; gate it to iOS
only: `Platform.OS === 'ios' && !Device.isDevice`. Comment explains Android
emulators with Google Play Services can receive FCM and must not be
re-broadened back to blocking them. Requires adding `Platform` from
`react-native` to `usePushToken.ts`'s imports (not currently imported there).

**Observability: every silent `return null` gets a distinct `console.warn`
line, prefixed `[push]` for grep-ability.** Three exit points in
`getRawFCMToken`, each already structurally distinct — just add a message to
each instead of a bare `return null`:
1. iOS simulator skip.
2. Permission not granted after the request flow (include the actual
   `finalStatus` value in the message — `'denied'` vs `'undetermined'` are
   different failure shapes worth telling apart).
The existing `ExponentPushToken` guard already throws with a descriptive
message — leave it as-is, it's already observable.

**A new shared `registerDeviceTokenSafe` helper, not three duplicated
try/catch blocks.** Added to `usePushToken.ts` alongside the existing
`registerDeviceToken` (which stays exported and unchanged — `login.tsx` /
`register.tsx` in all three apps call it directly today with their own local
try/catch and are out of scope, see below). `registerDeviceTokenSafe(client,
token)` wraps `registerDeviceToken`, resolves to `boolean` (never rejects),
and logs either outcome: `console.log('[push] Device token registered:',
token.slice(0, 12) + '...')` on success (truncated — no need to put the full
token in logs), `console.warn('[push] Device token registration failed',
err)` on failure. This single helper is what makes both "surface initial
failures" and "don't let a failure block listener setup" trivial at every
call site: swap `await registerDeviceToken(...)` for `await
registerDeviceTokenSafe(...)` and the function can no longer throw past that
line.

**Listener-setup ordering: wrap, don't reorder.** The three apps' `_layout`
files call `getRawFCMToken()` → `registerDeviceToken()` → attach
`addPushTokenListener` / `addNotificationReceivedListener` /
`addNotificationResponseReceivedListener` in that order, with Android channel
setup and (vendor only) iOS category registration ahead of all of it.
Moving registration to *after* listener setup would change already-tested
ordering (channels-before-first-notification, vendor's cold-start
`getLastNotificationResponseAsync` replay) for no benefit. Since
`registerDeviceTokenSafe` cannot throw, leaving the call in place and simply
swapping the function is sufficient — the listeners three lines below it now
always run. Simpler diff, same fix; reordering is rejected as needless extra
risk in vendor's larger effect.

**Re-attempt on foreground, without a second listener.** Add a
`tokenRegisteredRef = useRef(false)` next to each file's existing
`pushCleanupRef`. Set it from the return value of every
`registerDeviceTokenSafe` call (initial attempt and the rotation listener
callback). Reset it to `false` inside the push effect's own cleanup (the
`return () => { if (pushCleanupRef.current) {...} }` block) — that cleanup
only runs when the effect actually ran (i.e. was previously authenticated),
so a logout/login cycle correctly forces a fresh attempt for the new
session, and simulator/no-op runs (where the effect returns early) never
touch the ref.
- **Customer + vendor:** both already have a dedicated
  `AppState.addEventListener('change', ...)` effect driving `focusManager`.
  Extend that *same* callback: on `status === 'active'`, if
  `!tokenRegisteredRef.current && useAuthStore.getState().isAuthenticated`,
  call `getRawFCMToken()` again and, if it returns a token, call
  `registerDeviceTokenSafe` and store the result in the ref. `getRawFCMToken`
  re-checks `getPermissionsAsync()` first and only prompts if the status
  isn't already decided, so this does not re-prompt a user who's already
  denied — it just picks up a Settings-granted permission for free. This is
  the "reuse rather than adding a second listener" instruction — literally
  the same callback, same subscription.
- **Delivery:** has no such listener today. Add one dedicated
  `AppState.addEventListener('change', ...)` effect with the same reattempt
  body only (no `focusManager` call — delivery doesn't wire React Query's
  focus manager anywhere, and adding that wiring is a separate, larger change
  not asked for here). Comment states plainly that this listener exists
  solely for push reattempt so a future reader doesn't assume it's
  duplicating customer/vendor's RQ-focus wiring.

**`login.tsx` / `register.tsx` are out of scope.** All three apps also call
`getRawFCMToken` + `registerDeviceToken` directly after login/registration,
each already wrapped in a local `try { ... } catch { /* non-fatal */ }` that
does not block the auth flow. These six call sites are not the bug described
in #870 (which is specifically about `_layout.tsx`'s effect having no catch
and blocking listener setup) — they already degrade gracefully, just
silently. Leaving them untouched avoids scope creep into 6 additional files;
`_layout.tsx`'s effect fires within moments of `isAuthenticated` flipping
true regardless of which path set it, so it is still the backstop for these
call sites' silent failures.

## Verification

Device verification target is the **Android emulator** (`adb`), which after
this change should be able to register a token for the first time (it was
unconditionally blocked before). What's checkable locally without owner DB
access: run any of the three apps in the emulator, sign in, and watch Metro
(or `adb logcat | grep -i push`) for `[push] Device token registered:
<truncated-token>...` — its presence with a real (non-`ExponentPushToken`)
token value is the client-side proof this plan set out to produce. To
exercise the reattempt path: deny the notification permission prompt on
first launch, background the app, enable notifications for it in device
Settings, foreground the app again, and confirm the same log line appears
without a second permission prompt.

What needs server/owner access and is NOT part of this plan: confirming a
`PUT .../profile/device-token` actually reached the API and that "Push
skipped: user <id> has no FCM token" stops appearing for that user in
production logs — that's the DB/log-side half of the verification described
in the caveat above.

## must_haves

**truths:**
- An Android emulator (with Play Services) can register an FCM token; only
  iOS simulators are still blocked.
- Every path that exits `getRawFCMToken` without a token — iOS simulator,
  permission not granted — logs a distinct, greppable `[push]` reason.
- A failed or thrown initial registration no longer prevents the rotation,
  badge, or deep-link-tap listeners from attaching in any of the three apps.

  gets registered on the next foreground, without a duplicate `AppState`
  listener and without re-registering once already registered this session.
