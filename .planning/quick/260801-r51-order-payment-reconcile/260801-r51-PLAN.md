# Quick Task 260801-r51: Order-level payment reconcile cron (#872 step 2)

Closes step 2 of tesserix/Home-Chef-App#872.

## Goal

Step 1 (`fix/872-stale-order-gateway-gate`, already on this branch's base) stopped
the stale-order cron from cancelling a `payment_status=pending` order the gateway
actually captured — it now skips and logs `CAPTURED PAYMENT` loudly, leaving the
row `pending` forever. Nothing settles it. Settlement is client-verify-only (no
webhooks configured — 0 hits/24h), so a lost callback (app killed, network drop,
dismissed checkout sheet after Cashfree/Razorpay already captured) currently has
no path to ever complete.

This PR adds that path: a cron that finds captured-but-unconfirmed orders and
settles them through the SAME transactional core the HTTP verify legs use. Doing
that requires extracting the settle core out of `handlers` (which `services`
cannot import) into `services` — that extraction is the point of this PR, not a
side effect.

## Hard boundary — read this before touching anything

**Forward reconcile only.** This cron only ever touches rows where
`payment_status = 'pending'`. It NEVER selects a `status = 'cancelled'` row.

The stale cron, before step 1, wrongly cancelled captured orders
(`status=cancelled`, `payment_status=failed`, `cancel_reason='payment not
completed'`, non-empty `razorpay_order_id`, `refund_amount=0`). Those need a
**REFUND**, not a settle — the order was cancelled, capacity released, the chef
never cooked. That backfill is a separate, owner-gated task blocked on a
production audit query nobody has run yet.

**Do not** in this task: sweep/refund/resurrect cancelled orders, touch the
400-vs-502 error signalling in `verifyCashfreePayment`, configure webhooks, add
Stripe support to this cron (Stripe orders key off `stripe_payment_intent_id`,
never `razorpay_order_id` — out of this cron's predicate by construction; note it
as a known gap, do not special-case it), run `golangci-lint` (no config exists —
do not add one), or run `npx prettier` (reformats whole files).

## Extraction design (read before Task 1)

**What moves to `services` (new file `order_payment_settle.go`), exported exactly
as far as `handlers` still needs to call it:**

- `CompletionBlockedStatuses` (var, was `completionBlockedStatuses`) — handlers'
  webhook paths query against it directly.
- `NotifyChefNewOrderTx`, `CompleteOrderPaymentTx` — handlers still calls these
  directly for the Stripe and full-wallet paths, which are OUT of this task's
  scope and stay in `handlers`.
- `CompleteRazorpayOrderTx`, `CompleteCashfreeOrderTx` — exported for
  simplicity/consistency even though after Task 3 they're only called from
  within this same new file; no external caller needs them once the rewire
  lands, but there's no reason to downgrade them to unexported mid-plan.
- `ChefNetPayoutFor` — NOT moved, already lives in `services` and is exported;
  `handlers`' local one-line wrapper `chefNetPayout` is deleted, its 7 call
  sites (3 production, 4 test) call `services.ChefNetPayoutFor` directly.
- `OrderSettlements`, `ApplyChefRecoveryDeduction` — moved. `OrderSettlements` is
  used at BOTH order-CREATE time (`createRazorpayPayment`,
  `createCashfreePayment` — pricing the Route split before capture) and at
  settle time (inside `SettleOrderWallet`, the post-capture top-up plan). Both
  callers stay working via `services.OrderSettlements(db, order)`.
- `DebitOrderWallet`, `SettleWalletTopUps`, `settleWalletTopUpsWith` (kept
  unexported — no caller outside this file after the move),
  `SettleOrderWallet` — moved. `handlers.settleFullWalletOrder` (stays in
  handlers, writes JSON) calls `services.DebitOrderWallet` /
  `services.SettleWalletTopUps` directly; webhook paths call
  `services.SettleOrderWallet` directly.
- `SettleCashfreeOrder(order *models.Order) (bool, string)` — the full "ask
  Cashfree by order id, gate, complete, settle wallet" core. Both existing
  callers (`finishCashfreeFromGateway`, `verifyCashfreePayment`) already pass an
  id that equals `order.RazorpayOrderID` by the time they call it (verified —
  `finishCashfreeFromGateway`'s `cfOrder` was fetched BY `order.RazorpayOrderID`;
  `verifyCashfreePayment` checks `order.RazorpayOrderID != cfOrderID` and bails
  before calling it) — so the redundant id parameter is dropped. The cron calls
  it exactly the same way, with no parameter at all.
- `SettleRazorpayOrderFromPayment(order *models.Order, payment *PaymentResponse)
  (bool, string)` — NEW. Takes an already-fetched `PaymentResponse` (mirrors
  Cashfree's binding-gate-then-complete-then-settle shape) but does **not**
  fetch it itself, because HOW it's fetched differs by caller:
  `verifyRazorpayPayment` calls `rz.FetchPayment(paymentID)` (client-supplied
  id, single lookup — unchanged, exact same Razorpay endpoint hit as today); the
  cron calls `rz.FetchOrderPayments(order.RazorpayOrderID)` and picks the first
  `status == "captured" && OrderID == order.RazorpayOrderID` entry (no client id
  to look up — same discovery mechanism `meal_plan_advance_reconcile_cron.go`
  and `stale_order_cron.go` already use). Unifying on `FetchOrderPayments` for
  BOTH callers was considered and rejected: it would change which Razorpay
  endpoint the HTTP verify leg calls and could match a DIFFERENT captured
  payment than the one the client is claiming when an order has multiple
  attempts — a real behavior change on the money-critical path, not just a
  message-text difference.

**Message-text note (deliberate, not a regression):** `verifyRazorpayPayment`
today builds its own bespoke rejection strings (`"Payment not captured, status:
%s"`, `"Payment amount does not match the order total"`). Once it routes through
`ValidateCapturedPayment` via `SettleRazorpayOrderFromPayment`, those become the
SAME generic strings Cashfree already returns (`"Payment not captured"`,
`"Payment amount does not match the expected amount"`). Grep-verified: no test
in `handlers/*_test.go` asserts on this exact text, only on HTTP status code and
resulting DB state (`payment_status`). This unifies the codebase onto ONE
binding-gate implementation, which is the point of the task. It also means a
Razorpay binding/amount rejection now gets `ValidateCapturedPayment`'s log line
for free (today it logs nothing on that branch) — a strict improvement for the
cron's "loudly logged" underpayment requirement (Task 4), not a regression.

**Post-transaction side effects — what's in the core vs. what stays out:**
`MaybeGrantReward`, `StartOrderSaga`, and `SettleOrderWallet` are ALL already
idempotent per their own doc comments (keyed per-order / per-(order,account)),
so they belong INSIDE `SettleCashfreeOrder`/`SettleRazorpayOrderFromPayment` —
every caller (HTTP verify, HTTP create-leg recovery, cron) wants all three, and
duplicating that list at three call sites is exactly the "two implementations"
this task exists to avoid. `CaptureBackgroundError` on a transaction-persist
failure moves with them (same reasoning — it's already how both existing
callers handle it). The chef push + `order.paid` emit stay where they've always
lived: inside `CompleteOrderPaymentTx`'s guarded transition, gated on
`RowsAffected>0` so exactly one caller (whichever of cron/webhook/verify wins
the race) fires them.

**Idempotency — no new mechanism invented.** Two layers, both pre-existing:
(1) **Query-level**: once a settle succeeds, `payment_status` flips to
`completed`, so the cron's own `WHERE payment_status = 'pending'` excludes the
row on the next tick — it's never re-selected. (2) **Transaction-level
(belt-and-braces)**: `CompleteOrderPaymentTx`'s guarded `UPDATE ... WHERE
payment_status NOT IN (completed, refunded)` returns `RowsAffected==0` if a
concurrent webhook/verify/prior batch row in the SAME tick already completed it
— `SettleCashfreeOrder`/`SettleRazorpayOrderFromPayment` still return `(true,
"")` in that case (matching today's `settleCashfreeOrder` behavior exactly,
which does not branch on the inner bool either) because `MaybeGrantReward` /
`StartOrderSaga` / `SettleOrderWallet` are no-ops on a repeat and the chef
push/`order.paid` emit is what's actually guarded. The cron adds NO separate
dedup table, lock, or claim — it relies on exactly these two layers, same as
every other completion path.

**Grace/interval — justified against the two constants by name.**
`staleOrderThreshold = 30 * time.Minute` (`stale_order_cron.go`) is when step 1
gives up waiting for the client verify and starts asking the gateway before
cancelling; `staleOrderInterval = 10 * time.Minute` is how often it ticks. This
cron uses `orderPaymentReconcileGrace = 5 * time.Minute` and
`orderPaymentReconcileInterval = 5 * time.Minute`: worst case, a lost callback
is discovered and settled within grace+interval = 10 minutes of the order being
created — a third of `staleOrderThreshold`, and comfortably before the stale
cron's OWN first look at the row. That makes step 1's gateway-gate genuinely
belt-and-braces (a captured order it would otherwise leave `pending` forever is
already settled by the time it gets there) rather than the primary defence.

## Threat model (lightweight — no new trust boundary)

| Boundary | Description |
|---|---|
| cron → Cashfree/Razorpay APIs | Outbound only; response is external data fed into the settle decision. Identical trust posture to the existing HTTP verify legs and to step 1's stale-order gate. |

| Threat | Category | Disposition | Notes |
|---|---|---|---|
| A captured payment is settled against the WRONG order (replay across orders) | Integrity | mitigate | `ValidateCapturedPayment`'s order-id binding check, now the ONE implementation every settle path (HTTP + cron) shares — pinned by Task 4 test 3. |
| The extraction silently changes HTTP verify behavior (status code, DB state, side effects) | Integrity | mitigate | Task 3's regression net is the FULL existing `go test ./...` suite, run unmodified for the Cashfree/Razorpay HTTP paths — grep-verified those test files call none of the moved symbols directly. |
| The cron accidentally reaches the cancelled-order backfill set | Integrity / money | mitigate | Query predicate `payment_status='pending' AND status NOT IN (cancelled,...)` structurally excludes it; pinned by Task 4 test 9 with a zero-gateway-hit assertion. |
| Gateway outage causes an order to stay unsettled indefinitely | Availability | accept | Same trade-off `meal_plan_advance_reconcile_cron.go`/`stale_order_cron.go` already accept; loud log on non-trivial rejection reasons makes it observable; the order is still safe (money captured, order pending, nothing lost) while unsettled. |
| Logging captured payment id / gateway order id on rejection | Information disclosure | accept | Same class of identifier already logged throughout this package; no card data, no PII. |
