# Sockets must not give up permanently (#892)

## Goal

Every real-time socket stops reconnecting forever after a handful of consecutive
failures — roughly 12 seconds of bad connectivity (a lift, a tunnel, a carrier
handover). Live updates are then dead for the whole session with no recovery
short of a restart, and nothing tells the user.

Replace the hard cap with **capped exponential backoff that retries
indefinitely** while the hook is mounted and enabled.

## Current state (verified on `main` @ `21f09027`)

| File | Cap | Delay | After the cap |
|---|---|---|---|
| `apps/mobile-customer/hooks/useOrderStatusWS.ts` | `MAX_WS_FAILURES = 4` | 3000ms fixed | **stops forever, no fallback** |
| `apps/mobile-customer/hooks/useOrderTrackingWS.ts` | `MAX_WS_FAILURES = 3` | 2000ms fixed | stops; activates polling fallback |
| `apps/mobile-vendor/hooks/useLiveUpdates.ts` | `MAX_WS_FAILURES = 4` | 3000ms fixed | stops; falls back to SSE |

## The distinction that matters

The **fallbacks are good and must stay.** Polling (tracking) and SSE (vendor)
kicking in after N failures is correct degradation. The defect is that the socket
is never attempted again, so the app can never recover to real-time even when
connectivity returns.

So: keep fallback activation exactly as-is, and *additionally* keep retrying the
socket with backoff. `useOrderStatusWS` has no fallback at all, which is why it
is the worst case.

## Precedent to reuse — do not invent a new curve

`packages/mobile-shared/src/support/outbox.ts:38` already exports:

```ts
/** Capped exponential backoff for re-send attempts. */
export function backoffMs(attempts: number): number {
  return Math.min(30_000, 1_000 * 2 ** Math.max(0, attempts - 1));
}
```

## Tasks

### Task 1 — shared socket backoff helper (`packages/mobile-shared`)

- Export a socket reconnect-delay helper. Prefer **reusing `backoffMs`**; only
  add a variant if the socket curve genuinely needs different bounds — if so,
  justify the numbers in a comment and keep the same shape.
- Sensible target: first retry near the current fixed delay, growing to a ~30s
  ceiling. Never returns 0, never unbounded.
- **Add vitest tests** (monotonic growth, ceiling respected, sane value at
  attempt 1, no negative/zero). The suite is the only real test bed in mobile —
  keep it green; 4 failures (`auth-screens` ×3, `resolve-auth-error` ×1) are
  PRE-EXISTING, do not chase them and do not let the count grow.

### Task 2 — apply to all three sockets

For each of the three files:
- Remove the permanent give-up. Reconnect indefinitely while mounted and
  `enabled`, scheduling with the shared helper keyed on consecutive failures.
- **Preserve every existing fallback trigger** (polling / SSE) unchanged.
- Reset the failure counter on a successful open (already done today).
- **Reset on app foreground** so returning to the app retries immediately rather
  than waiting out a long backoff. Reuse existing `AppState` wiring where the app
  already has it; add a narrowly-scoped listener only where it does not.
- Keep the #891 logging, but **fix the now-false give-up line** — it must no
  longer claim "no further reconnects". Log the scheduled delay instead.
- Clear timers on unmount (already done) — verify the backoff path does too.

## Out of scope

Socket auth/URLs/protocol; the notification-query auth gate (#869, merged);
removing or weakening the polling/SSE fallbacks; any `apps/api` change.

## Risk

Retrying forever must not become a hot loop or a battery drain: the ceiling and
the existing background-pause behaviour are what make it safe. Do not reduce the
ceiling below ~30s.
