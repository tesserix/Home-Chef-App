# Quick Task 260802-07q: Fix #696 Skip Eligibility IST Day Boundary Summary

**Fixed three independent bugs in the tiffin Skip flow: the client posted the API's RFC3339 instant straight through to a handler that only parses bare `YYYY-MM-DD` (Skip returned 400 on every attempt, regardless of eligibility), the Upcoming filter used device-local midnight instead of IST (offering an unskippable "today" on some device timezones), and — introduced while fixing the second bug — today's meal briefly disappeared from the list entirely instead of showing with no Skip control.**

## Accomplishments
- `isSkippableMealDay(dateISO, now)`, `isPastMealDay(dateISO, now)`, and `istCalendarDate(instant)` in `packages/mobile-shared` — pure, device-timezone-independent IST calendar-day arithmetic mirroring the server's `d.After(todayIST)` rule bit-for-bit; 10 vitest cases cover UTC-8 device, IST device, both sides of IST midnight, past/today/future, and the exact RFC3339 shape the API sends
- `subscriptions.tsx` Upcoming list now separates two concerns: which days are *listed* (`!isPastMealDay` — today stays visible) versus which days get a *Skip button* (`isSkippableMealDay` — strictly future only); today's row shows a quiet "Already started" label instead of a button or disappearing entirely
- `skipDay` now converts `f.date` (an RFC3339 UTC instant, the API's default JSON encoding of a `time.Time`) to a bare `YYYY-MM-DD` via `istCalendarDate` before POSTing — **this was the actual reason Skip never worked at all**: the server's `time.ParseInLocation("2006-01-02", req.Date, ist)` rejected the RFC3339 string with "extra text" on every single call, eligible or not. The original off-by-one day-boundary bug (Plan Tasks 1–2) was real but secondary to this.
- Client skip-error fallback and the server's `Skip` handler rejection string both corrected to describe the rule actually enforced ("day already started" / "hasn't started yet"), dropping all references to an unenforced "cutoff"

## Decisions Made
- Compared IST calendar dates as `YYYY-MM-DD` strings (`>`/`<` operators) rather than millisecond instants, so the client logic is a direct, auditable mirror of the server's `time.Date(...).After(...)` check on calendar days, not an independent instant-based reimplementation that could drift.
- Kept the explanatory "Upcoming" note ("Skip by the end of the day before.") above the list — it states the general timing rule before scanning rows, while the per-row "Already started" label is row-specific; deliberately not merged into one string since they answer different questions (when can I skip, vs. why can't I skip *this* one).
- Normalized the Skip payload date format in `skipDay` (the call site), not inside `useMealSubAction`'s shared `mutationFn` — the hook's `mutationFn` is reused by pause/resume/cancel, which don't have a `date` field, so keeping the conversion at the point where the raw `MealFulfillment.date` is available keeps the hook generic.
- Added `isPastMealDay` as a distinct exported predicate rather than inverting `isSkippableMealDay` inline at call sites, so "is this day in the past" is testable and named independently of "is this day skippable" — today is `false` for both, which is the whole point.

## Deviations from Plan

The coordinator identified two additional bugs during review, both fixed as follow-ups inside #696 scope (not part of the original plan's 3 tasks, but requested before merge):

### Auto-fixed Issues

**1. [Coordinator-directed, correctness] Skip payload was never in a format the server could parse**
- **Found during:** Coordinator review, after Task 3
- **Issue:** `GetFulfillments` serializes `[]models.MealSubscriptionFulfillment` directly (no DTO) — `Date time.Time` with `json:"date"` and no custom marshaler produces RFC3339 (e.g. `"2026-08-02T18:30:00Z"`). `skipDay` forwarded `f.date` unchanged to `POST /skip`, whose handler parses with `time.ParseInLocation("2006-01-02", req.Date, ist)` — this rejects any RFC3339 string with "extra text", so **every Skip call returned 400, regardless of eligibility**. The original day-boundary fix (Tasks 1–2) was real but never actually reachable in practice.
- **Fix:** Confirmed the premise (no DTO layer exists) by reading `GetFulfillments` and `MealSubscriptionFulfillment.Date`'s struct tag directly. Converted `f.date` to a bare `YYYY-MM-DD` via `istCalendarDate(new Date(f.date))` at the `skipDay` call site before calling `action.mutate`. Added a vitest case in `ist-calendar-date.test.ts` pinning the exact RFC3339-UTC-midnight-to-`YYYY-MM-DD` conversion, so a future refactor of either side can't silently reintroduce the mismatch.
- **Files modified:** `packages/mobile-shared/src/__tests__/ist-calendar-date.test.ts`, `apps/mobile-customer/app/subscriptions.tsx`
- **Verification:** `apps/mobile-customer` `npx tsc --noEmit` (0 errors), `packages/mobile-shared` vitest (4 pre-existing failures unchanged, 10/10 new+existing `ist-calendar-date` tests pass), `go build ./...` (unaffected, no server change needed for this fix)
- **Committed in:** `cd911d98` (helper + test), `327acabb` (call-site fix)

**2. [Coordinator-directed, regression from Task 2] Today's meal vanished from the Upcoming list**
- **Found during:** Coordinator review, after Task 2's filter change
- **Issue:** Task 2's filter (`f.status === 'scheduled' && isSkippableMealDay(f.date)`) correctly excludes today from *Skip eligibility*, but applying the same predicate to the *listing* filter also hid today's scheduled meal entirely — a regression versus the pre-fix behavior (which showed today with a broken Skip button). Hiding the most relevant row on the screen is worse than showing it without a working button.
- **Fix:** Added `isPastMealDay` (strictly-before comparison) and switched the listing filter to `!isPastMealDay(f.date)` (today-or-future), keeping `isSkippableMealDay(f.date)` as a separate per-row check that decides whether the row renders an `ActionBtn` or a quiet "Already started" `Text` label — no dead space, no urgency framing.
- **Files modified:** `packages/mobile-shared/src/utils/ist-calendar-date.ts`, `packages/mobile-shared/src/__tests__/ist-calendar-date.test.ts`, `apps/mobile-customer/app/subscriptions.tsx`
- **Verification:** Same three gates as above, all green.
- **Committed in:** `cd911d98` (helper + test), `327acabb` (rendering fix)
