# Quick Task 260801-p44: Gate the stale-order cron on a real gateway check (#872 step 1)

Closes step 1 of tesserix/Home-Chef-App#872.

## Goal

`runStaleOrderScan` in `apps/api/services/stale_order_cron.go` cancels every
`payment_status=pending` order older than 30 minutes and stamps it
`failed`/`cancelled` **without ever asking the payment gateway**. It infers
"nothing was captured" from our own DB row — which is exactly the field that's
wrong when Cashfree captures money, our client-side verify fails to land, and
(webhooks not configured) nothing else ever confirms the payment. 30 minutes
later this cron destroys the order and keeps the customer's money silently.

Fix: before cancelling, ask the gateway whether the order's stamped gateway
order id has a captured payment, and only cancel when the gateway confirms it
does **not**. An unknown answer (gateway error, gateway not configured) must
never cancel — it must skip and retry next tick.

## Hard boundary — read this before touching anything

**This PR does not settle captured-but-unconfirmed orders.** `apps/api/handlers`
imports `apps/api/services`; `services` never imports `handlers`. The settle
seam (`settleCashfreeOrder` / `completeCashfreeOrderTx` in
`handlers/payment_cashfree.go:347-431`) is unexported and lives in `handlers`.
Extracting it into `services` so this cron could call it would be a refactor of
the live payment-completion path — not a stop-the-bleeding fix.

So on "captured": **skip and log loudly**. Do not settle. Do not refund. Do not
mutate the row. The order stays `pending` exactly as it was. Actually settling
those orders is the next PR (an order-level reconcile cron modelled on
`meal_plan_advance_reconcile_cron.go`), which will do the extraction because
it's the point of that PR, not a side effect of this one.

**Do not** in this PR: settle/confirm captured orders, touch
`payment_cashfree.go`, change any 400-vs-502 error signalling, configure
webhooks, or write the reconcile cron. Those are tracked separately (#872
later steps).

## Decision table (implement exactly this)

| RazorpayOrderID | Gateway answer | Action |
|---|---|---|
| `""` (never stamped) | not asked | **cancel**, zero gateway calls |
| non-empty | captured payment found | **skip** — leave `pending`, log loudly, do not settle |
| non-empty | gateway says not captured | **cancel**, exactly as today (same field writes, same capacity + slot release) |
| non-empty | gateway fetch errored, OR gateway not configured for that mode, OR `PaymentProvider` normalizes to something this cron doesn't know how to ask (not cashfree/razorpay) | **skip** — never cancel on an unknown answer, log the error, retry next tick |

**Provider-mismatch / nil-gateway rule (explicit choice for this PR):** treat
BOTH "no gateway configured for this mode" and "provider is neither cashfree
nor razorpay" as the same **gateway-error skip** outcome, not as cancel. In
practice `Order.PaymentProvider` is `cashfree` or `razorpay` for every row that
could reach this cron with a non-empty `RazorpayOrderID` and
`payment_status=pending` (Stripe orders key off `StripePaymentIntentID`
instead; wallet-covered orders never sit `pending`), so this branch is a
defensive backstop, not a live path. It costs a possibly-permanent `pending`
row if a mode is left unconfigured forever — accepted, because that failure
mode is visible (a loud log every 10 minutes) and reversible (configure the
gateway, or handle it by hand), whereas wrongly cancelling a captured payment
is silent and, once the order is `cancelled`, requires manual reconstruction
of what happened. Same asymmetry `meal_plan_advance_reconcile_cron.go`'s
`GetRazorpayFor(p.Mode) == nil → skip` already accepts.

## Tasks

### Task 1 — Gate the cancel path on a real gateway check

- **files:** `apps/api/services/stale_order_cron.go`
- **behavior:**
  - `decideStaleOrderAction(hasGatewayOrderID bool, capturedPaymentID string,
    gatewayErr error) staleOrderAction` is a **pure** function (no DB, no
    gateway I/O) implementing exactly the decision table above:
    `!hasGatewayOrderID → cancel`; `gatewayErr != nil → skipError`;
    `capturedPaymentID != "" → skipCaptured`; else `cancel`.
  - `staleOrderCapturedPayment(order *models.Order) (capturedPaymentID
    string, err error)` does the I/O: switches on
    `models.NormalizeProvider(order.PaymentProvider)`.
    - `PaymentProviderCashfree` → `GetCashfreeFor(order.Mode)`; nil → return
      an error (nil-gateway case). Else `SuccessfulPayment(order.RazorpayOrderID)`;
      on success with a non-nil payment, return `payment.CFPaymentID.String()`;
      nil payment → return `("", nil)` (not captured).
    - `PaymentProviderRazorpay` → `GetRazorpayFor(order.Mode)`; nil → return
      an error. Else `FetchOrderPayments(order.RazorpayOrderID)`, then
      `capturedPaymentFor(pays, order.RazorpayOrderID)` (the existing helper
      from `meal_plan_advance_reconcile_cron.go` — do not duplicate it).
    - anything else → return an error naming the unrecognised provider (the
      provider-mismatch backstop from the decision table).
- **action:**
  Define `staleOrderAction` (int-backed, three named consts: cancel,
  skipCaptured, skipError) and the two functions above in
  `stale_order_cron.go`. Extract the query + per-row loop out of
  `runStaleOrderScan` into `runStaleOrderScanWithDB(ctx context.Context, db
  *gorm.DB, now time.Time) (expired, skippedCaptured, skippedError int)` — same
  shape as `refundUnacceptedOrders(ctx, db, now)` in
  `unaccepted_order_cron.go`. Inside the per-row loop: if
  `order.RazorpayOrderID == ""`, decide with `hasGatewayOrderID=false` and no
  gateway call (preserves today's zero-latency abandoned-checkout path);
  otherwise call `staleOrderCapturedPayment`, feed the result into
  `decideStaleOrderAction`, and branch:
  - `cancel` → run the EXACT existing transaction (same three field writes,
    same `ReleaseCapacity` / `ReleaseSlot` calls, same log line shape).
  - `skipCaptured` → log at `stale-order:` prefix with a clearly greppable
    marker (e.g. `CAPTURED PAYMENT`), including order number, gateway order
    id, provider, mode, and the captured payment id. Do not touch the row.
  - `skipError` → log the gateway error with the same order identifiers minus
    the payment id (there isn't one). Do not touch the row.
  `runStaleOrderScan(ctx)` becomes a thin wrapper: keep its `defer
  recover()`, call `runStaleOrderScanWithDB(ctx, database.DB, time.Now())`,
  and log a summary line reporting all three counts (expired, skipped as
  captured, skipped on error) — the current single "expired %d" line
  under-reports once skips exist.
  Rewrite the package header comment (lines 1-11): it currently says cancelling
  happens because "no payment was captured" — that's now false. Explain the
  real chain (client-verify-only settlement, no webhooks, so this cron is the
  last gate) and the new gateway-confirms-before-cancelling behavior. Also
  correct the inline comment on line 92 ("no payment was captured, so nothing
  to refund") which is only true on the confirmed-not-captured branch now.
- **verify:** `cd apps/api && go build ./...`
- **done:** File compiles; `runStaleOrderScan` still matches its existing
  signature (`StartStaleOrderCron` calls it unchanged); no other file needs
  edits (`capturedPaymentFor` is package-private and already in scope).

## must_haves

**truths:**
- A captured-but-unsettled order is never cancelled by this cron — it stays
  `pending` and a loud, greppable log line names it.
- An order the gateway confirms was never paid is cancelled exactly as it was
  before this change (same fields, same capacity/slot release).
- A gateway error or an unconfigured gateway slot never results in a
  cancellation — the order is retried on the next tick.
- An order with no gateway order id ever stamped is cancelled with zero
  gateway calls (no latency regression on the common abandoned-checkout path).
- Cashfree orders are asked of Cashfree and Razorpay orders are asked of
  Razorpay — never cross-checked against the wrong gateway.

## Threat model (lightweight — no new trust boundary)

| Boundary | Description |
|---|---|
| cron → Cashfree/Razorpay APIs | Outbound only; response is external data fed into the cancel/skip decision. |

| Threat | Category | Disposition | Notes |
|---|---|---|---|
| Gateway response misread as "not captured" when it was captured | Integrity | mitigate | This IS the fix: `decideStaleOrderAction` is pure/unit-tested against all four decision-table branches; "unknown → never cancel" is the load-bearing rule. |
| Gateway outage causes an order to skip forever | Availability | accept | Same trade-off `meal_plan_advance_reconcile_cron.go` already accepts; loud log every tick makes it observable, and cancelling on an unknown answer is strictly worse (silent money loss). |
| Logging captured payment id / gateway order id | Information disclosure | accept | Same class of identifier already logged elsewhere in this file and in `meal_plan_advance_reconcile_cron.go`; no card data, no PII. |
