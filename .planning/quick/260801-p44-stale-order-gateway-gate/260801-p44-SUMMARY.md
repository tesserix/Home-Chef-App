# Quick Task 260801-p44: Gate the stale-order cron on a real gateway check Summary

**`runStaleOrderScan` now asks Cashfree/Razorpay whether a captured payment exists before cancelling a pending order, and an unknown answer (gateway error, unconfigured slot, unrecognised provider) never reaches the cancel transaction — only a confirmed "not captured" or an order with no gateway order id ever stamped does.**

## Accomplishments

- Extracted the query + per-row loop into `runStaleOrderScanWithDB(ctx, db, now) (expired, skippedCaptured, skippedError int)`, matching the `unaccepted_order_cron.go` seam-and-test shape. `runStaleOrderScan` is now a thin wrapper (defer/recover + real `database.DB`/`time.Now()` + a three-count summary log).
- Added `decideStaleOrderAction` — a pure, DB/IO-free function implementing the plan's decision table exactly (`!hasGatewayOrderID → cancel`; `gatewayErr != nil → skipError`; `capturedPaymentID != "" → skipCaptured`; else `cancel`).
- Added `staleOrderCapturedPayment(order)` — switches on `models.NormalizeProvider(order.PaymentProvider)`, asks `GetCashfreeFor`/`GetRazorpayFor` for the order's `Mode`, reuses `capturedPaymentFor` (from `meal_plan_advance_reconcile_cron.go`) for the Razorpay leg, and returns an error for a nil gateway slot or an unrecognised provider (the decision table's explicit provider-mismatch backstop).
- Rewrote the package header comment and the inline cancel-branch comment to describe the real chain (client-verify-only settlement, no webhooks, this cron is the last gate) instead of the now-false "no payment was captured" framing.
- Wrote 8 tests in `stale_order_cron_test.go`: a pure decision-table test (4 sub-cases) plus the plan's 6 required integration scenarios (captured→skip, not-captured→cancel, gateway error→retry×2, unconfigured mode→skip, empty gateway-order-id→zero gateway calls, and provider routing proven both directions with hit counters on the "wrong" gateway's test server).

### Auto-fixed / adapted

**1. [Rule 3 - blocking environment constraint] Omitted capacity/slot-release table assertions in the "not captured → cancel" test**
- **Found during:** Task 2, writing `TestStaleOrderSweep_NotCaptured_CancelsExactlyAsBefore`.
- **Issue:** The plan asks that scenario to assert capacity + slot release by seeding a capacity row and checking it via the same query pattern `ReleaseCapacity`/`ReleaseSlot` leave behind. Both of those functions run `UPDATE ... SET x = GREATEST(0, x - ?)` — a Postgres-only builtin sqlite does not have. Any order seeded with `Items` or a non-empty `DeliverySlot` would make the entire cancel transaction fail with "no such function: GREATEST", not release anything measurable. This is a pre-existing, already-documented constraint in this exact package: `unaccepted_order_cron_test.go`'s `seedPaidPendingOrder` explicitly seeds zero items and an empty `delivery_slot` for the identical reason, and no test anywhere in `apps/api/services` exercises `ReleaseCapacity`/`ReleaseSlot`'s success path against sqlite.
- **Fix:** Followed the same established pattern — `seedStaleOrder` seeds zero order items and no delivery slot in every scenario, and the "not captured → cancel" test asserts only the order row's own field writes (`status`, `payment_status`, `cancel_reason`, `cancelled_at`), which is exactly what Task 1's cancel branch changed. The file header documents this explicitly so a future reader doesn't mistake the omission for an oversight. The capacity/slot-release code path itself is untouched by this PR (same `ReleaseCapacity`/`ReleaseSlot` calls, same call sites, same order — see the diff in `stale_order_cron.go`), so its correctness is unaffected by this change; it remains covered by the same environment limitation every sibling cron test already accepts.
