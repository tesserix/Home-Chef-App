# 260801-c27-notif-401 Summary

GH #869 (re-scoped, two fixes): stop the unauthenticated notification-query 401 storm at the source, and make the notification WebSocket (and its 3 siblings) observable so silent give-ups are greppable.

## What changed

### Fix 1 — auth gate + no-retry-on-401

**Where the gate lives and why:** `useNotificationList` / `useUnreadCount` in `packages/mobile-shared/src/hooks/useNotifications.ts` now accept a second `NotificationQueryOptions` argument with an optional `enabled` flag, threaded straight into React Query's `enabled` option. Every call site (2 in customer, 2 in vendor) now reads a reactive `const isAuthenticated = useAuthStore((s) => s.isAuthenticated);` selector and passes `{ enabled: isAuthenticated }`. Both Home screens are reachable while signed out (customer explicitly supports guest browsing; vendor's dashboard mounts before the auth check settles), so the query was previously firing on every unauthenticated mount. Gating at the hook call site (not globally) keeps the change local to the two queries that were storming — nothing else in either app's query behavior changes.

`useNotificationSocket({...})` calls were deliberately left untouched (per plan) — the socket already self-gates internally on `getToken()` returning a token, so adding `enabled` there would have been redundant, and touching its connection logic was explicitly out of scope.

**Where the no-retry-on-401 rule lives and why scoped, not global:** `shouldRetryNotificationQuery(failureCount, error)` is a new exported pure function in `useNotifications.ts`, passed as the `retry` option to both queries. It duck-types the error's `response.status` (no `axios` value import needed) and returns `false` unconditionally on a 401, `false` once `failureCount >= 2` for anything else (matching the apps' existing global `QueryClient` default of `retry: 2`), and `true` otherwise. This is scoped to these two queries rather than changed globally in `_layout.tsx` because a 401 from an unrelated authenticated endpoint might legitimately want the existing global retry behavior — the storm was specific to these two queries firing while logged out, so the fix is specific to them too.

### Fix 2 — WS lifecycle observability

Added connect / error / close-and-reconnect / terminal-give-up logging to all 4 hooks, one consistent bracket prefix each, following the existing `[push]` convention from `usePushToken.ts`. `console.info` for connect, `console.warn` for error/reconnect, `console.error` for the terminal give-up (or its equivalent). No `console.log` anywhere; no Bearer token, header, or message payload logged — only prefix, URL (notif-ws only, per plan interface note), mode/orderId (non-PII), and numeric failure counters.

| Hook | Prefix | Give-up equivalent |
|---|---|---|
| `useNotificationSocket` (shared) | `[notif-ws]` | Logs and stops reconnecting once `failures.current >= MAX_WS_FAILURES` (previously a bare `return;` with only a comment) |
| `useOrderStatusWS` (customer) | `[order-ws]` | Logs "giving up... no further reconnects" when `enabled && failureCount.current >= MAX_WS_FAILURES` (previously silent — the `onclose` handler did nothing in that branch) |
| `useOrderTrackingWS` (customer) | `[tracking-ws]` | Logs "giving up... falling back to polling" in `onerror` at the point `setUseFallback(true)` is called |
| `useLiveUpdates` (vendor) | `[live-ws]` | Logs "falling back to SSE after N WS failures" at the point `openEventStream(...)` is invoked instead of a new WS |

No `MAX_WS_FAILURES`, `RECONNECT_DELAY_MS`, reconnect predicate, or auth mechanism was changed in any of the 4 hooks — this task was observability-only, per the plan's critical correctness notes.
