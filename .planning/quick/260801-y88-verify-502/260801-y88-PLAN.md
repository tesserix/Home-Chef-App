# Quick Task 260801-y88: Distinguish upstream gateway failure from "not paid" in verify (#872 final item)

Closes tesserix/Home-Chef-App#872.

## Goal

`services.SettleCashfreeOrder` (the shared "ask the gateway, settle" core built
in `fix/872-order-payment-reconcile-cron`) collapses two different outcomes
into one `(false, msg)`: the mandatory `cf.SuccessfulPayment` fetch erroring
(transport failure, timeout, 5xx, unparseable body — **retryable**) and the
fetch succeeding but reporting no captured payment (**terminal — genuinely
unpaid**). Both callers — `verifyCashfreePayment` and
`finishCashfreeFromGateway` (the create-leg already-PAID recovery) — then
answer `400` for either, contradicting `verifyCashfreePayment`'s own doc
comment, which already claims "a gateway outage surfaces as a 502 rather than
being waved through."

Fix: make `SettleCashfreeOrder` tell its callers WHICH kind of failure
happened, and have both HTTP callers answer 502 for the retryable kind, 400
for the terminal kind — with a decision for "gateway not configured" that
matches this codebase's existing sibling checks (503, not 400).

## Hard boundary — read this before touching anything

**Client-visible behavior does not change** except the two status codes and
their messages. No mobile app change: `apps/mobile-customer/lib/payment.ts`
deliberately swallows verify failures (`// ignore — the result screen confirms
via polling`), so today a customer sees no difference between 400 and 502 on
this call — this fix makes the SERVER truthful and stops a future client
branching on the wrong signal, it does not change today's UX. Do not touch the
mobile app.

**Do not** in this task: touch the create-leg's happy-path Cashfree order
creation, the webhook handlers, the stale-order cron, or the order-payment
reconcile cron's SETTLE logic (only its call-site signature needs a
one-line update to compile against the new 3-return signature — see Task 1).
Do not touch Stripe's verify leg (`verifyStripePayment`) — it is not named in
the issue and its `FetchPaymentIntent` failure path is out of scope; note that
as a known, deliberately-unaddressed parallel gap, do not "fix" it here.
Do not run `golangci-lint` (no config exists — do not add one). Do not run
`npx prettier`.

## Design — how the retryable/terminal distinction is carried

Change `SettleCashfreeOrder`'s signature from `(bool, string)` to `(bool,
string, error)` — the Go-idiomatic "error last" shape this codebase's own
convention already documents (see `CLAUDE.md` "Go functions return `(Result,
error)` tuple; error is last"), and the smallest change that keeps the
existing `(bool, string)` reason contract intact for the one caller that does
not care about HTTP status (`order_payment_reconcile_cron.go`).

Two new package-level sentinel errors in `order_payment_settle.go`, following
this codebase's existing `var ErrX = errors.New(...)` convention (see
`services.ErrAppleNotConfigured`, `services.ErrChefBookUnavailable`,
`services.ErrSlotFull`, etc. — no HTTP-status-carrying error TYPE exists
anywhere in this codebase, so a struct would be inventing a new pattern where
a sentinel already fits):

- `ErrPaymentGatewayUnavailable` — the gateway client for this mode is not
  configured. Server-side misconfiguration, not something the client caused.
- `ErrPaymentGatewayFetchFailed` — the mandatory server-side fetch of the
  gateway's own payment record failed (transport error, timeout, 5xx,
  unparseable response). Retryable. Wrapped with `%w` around the underlying
  `cf.SuccessfulPayment` error for the log line, exactly like
  `services/push.go`'s `ErrPushTokenInvalid` wrapping already does in this
  codebase.

`SettleCashfreeOrder` returns `nil` error on every TERMINAL branch (`payment
== nil`, any `ValidateCapturedPayment` rejection, and the success path) — so
`errors.Is` against the two sentinels is the only thing a caller needs to
decide status.

A small handler-local helper in `payment_cashfree.go`,
`cashfreeSettleStatus(err error) int`, maps the error to a status code
(`ErrPaymentGatewayUnavailable` → 503, `ErrPaymentGatewayFetchFailed` → 502,
`nil`/anything else → 400, unchanged). This mapping lives in `handlers`, not
`services` — matches this codebase's own layer table ("Handler: HTTP parsing,
validation, response formatting" vs. "Service: business logic"), and mirrors
how `verifyStripePayment`/`verifyRazorpayPayment` already decide their own
status codes locally rather than services choosing them.

**"Payment gateway not configured" → 503, not the current 400.** This is a
deliberate behavior change, justified by the codebase's OWN existing sibling
checks for the identical string: `createCashfreePayment` (line 55),
`verifyRazorpayPayment` (line 462), and `verifyStripePayment` (line 504) all
already answer `503 "…gateway not configured"` / `"Payment gateway not
configured"` for exactly this condition. `SettleCashfreeOrder` was the one
outlier answering 400 for it. This change makes all four call sites agree.

## Threat model (lightweight — no new trust boundary)

| Boundary | Description |
|---|---|
| client → `POST /payments/order/:orderId/verify` | Unchanged. The client still supplies only an order id (Cashfree) or paymentId/orderId/signature (Razorpay); the gateway's own record remains the sole authority for "was this paid". This task changes status codes and error text only, never which input is trusted. |
| API → Cashfree/Razorpay APIs | Outbound only; a 5xx/transport failure now maps to a distinct sentinel error instead of being indistinguishable from a clean "not captured" answer. |

| Threat | Category | Disposition | Notes |
|---|---|---|---|
| A `ValidateCapturedPayment` binding/amount rejection is accidentally swept into the retryable (502) bucket, making a replay or underpayment rejection look retryable | Integrity | mitigate | `ValidateCapturedPayment` never returns through the new error-wrapping branch — its rejection path explicitly returns `nil` error, verified by the four unmodified `TestVerifyCashfreePayment_Rejects*` tests still asserting 400 (Task 3, item 4). |
