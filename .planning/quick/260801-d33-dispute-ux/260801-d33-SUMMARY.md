## (a) How errors are surfaced

`onDisputeSubmit`'s `onError` mirrors `onRequest`'s existing idiom exactly:

```ts
onError: (err) =>
  showAlert(
    "Couldn't raise the dispute",
    friendlyErrorMessage(err, 'Please try again in a moment.'),
  ),
```

`friendlyErrorMessage` (`apps/mobile-customer/lib/errors.ts`, unchanged) is
the only place a caught error is read — it strips transport noise (status
codes, axios/network phrasing) and prefers the API envelope's `message`/
`error` field, falling back to a calm generic line. No raw status code, HTTP
transport string, or `err.message` reaches the UI directly.

## (b) How pending is gated

`dispute.isPending` (from `useDisputeCancellation()`) is threaded into
`StatusView` as a new `disputePending: boolean` prop. The "Dispute the refund
amount" `Pressable` (the `'approved'` branch of `StatusView`) gets:
- `disabled={disputePending}`
- `android_ripple={disputePending ? undefined : { color: LINK_RIPPLE, ... }}`
  (new `LINK_RIPPLE` constant, translucent coral, matching the existing
  `BTN_RIPPLE` convention)
- the label swapped for a small `ActivityIndicator` while pending, via a new
  `linkRow` flex-row wrapper `View` (object-style array-merged `style={[...]}`
  on an inner `View`, per the project's iOS-Pressable gotcha — never a
  function returning a bare array).

A double-tap while pending cannot fire a second POST: the control is
`disabled` for the whole in-flight window.

## (c) Reason-collection UI and the stale anti-modal comment

Built `DisputeReasonSheet` directly on `SheetBase` (from
`@homechef/mobile-shared/ui`), `forwardRef<SheetHandle, ...>`, structurally
mirroring `ReportSheet` (chips + optional free-text) but with dispute-specific
copy and `customerColors` styling (not `theme.colors`/herb, which belongs to
the older token set `ReportSheet` uses).

`CancellationSection.tsx`'s header comment previously read "Inline expansion
— no bottom-sheet — deliberately, to avoid the modal-provider class of
crash." That was written against `@gorhom/bottom-sheet`, which silently
no-ops on this app's gorhom 5.2.8 + reanimated 4.4.1 pairing. `SheetBase` was
rewritten (commit `97b3898d`) to a plain RN `Modal` + `Animated`
implementation with zero gorhom/reanimated dependency, and is now the
pervasive sheet pattern in this app — including on the exact screen that
renders `CancellationSection` (`app/order/[id]/index.tsx`). I updated the
comment in place to explain this rather than leave a stale warning that would
mislead the next person touching this file; the "Request cancellation" inline
expansion itself is untouched.

## (d) Required vs. optional reason

4 preset chips (`amount_too_low`, `disagree_with_decision`,
`refund_not_arrived`, `other` = "Something else") — one is required to enable
"Submit dispute" (`disabled={!reason}`). An optional free-text `TextInput`
(`maxLength={500}`) lets the customer elaborate. On submit, the combined
string is `` `${label} — ${details.trim()}` `` when details are present, or
just the label otherwise — this guarantees a non-empty, human-readable reason
reaches the admin arbitration queue on every path, while "Something else"
with zero typing is always tappable so no customer is ever stranded.

## Addition: no second dispute on an already-disputed order

Per the owner's added requirement, implemented in `onDisputeSubmit`'s
`onSuccess` (`CancellationSection.tsx`):

```ts
onSuccess: () => {
  qc.setQueryData<CancellationRequest | null>(
    ['order', orderId, 'cancel-request'],
    (old) => (old ? { ...old, status: 'disputed' } : old),
  );
  showAlert('Dispute raised', 'Our team will review it and get back to you.');
},
```

- **Query key used:** `['order', orderId, 'cancel-request']` — the exact key
  `useCancellationRequest` already reads from and `useDisputeCancellation`'s
  own `onSuccess` already invalidates. No new key was invented.
- **Status value written:** `'disputed'` — the real value the server sets
  (`DisputeCancellation` in `apps/api/handlers/cancellation.go` sets
  `status = disputed`, confirmed by reading that handler; no backend file
  was touched).
- **Why optimistic, not just invalidate:** `useDisputeCancellation`'s hook-level
  `onSuccess` already calls `qc.invalidateQueries({ queryKey: [...] })`, but
  that only *marks the query stale and triggers a background refetch* — it
  does not synchronously update the cached value. Between the success alert
  and that refetch landing, `request.status` was still `'approved'`, so the
  `StatusView` `'approved'` branch (Pressable, now `disabled={disputePending}`
  only while the *mutation itself* is in flight) kept rendering and stayed
  tappable — including indefinitely if the refetch never lands (offline,
  dropped request). Writing the new status directly into the cache via
  `setQueryData` flips `StatusView`'s switch to the `'disputed'`/
  `'admin_review'` branch ("Under review") immediately, on the same render
  pass as the success alert. The existing `invalidateQueries` in the hook is
  kept unchanged as reconciliation against the server's actual row.
- **Server backstop unchanged:** `DisputeCancellation` still 409s a second
  dispute attempt regardless (`cr.Status != approved`); this change only
  stops the client from *offering* an action that cannot succeed, per the
  addition's framing — not a new server guarantee.
