# Quick Task 260801-z41: Stop telling customers a captured payment "failed" — Summary

Closes tesserix/Home-Chef-App#887. Branch: `fix/887-payment-still-confirming`.

## One-liner

Split the payment result screen's single `'failure'` bucket into a real
server-declined `'failure'` (unchanged, keeps Retry) and a new honest
`'confirming'` state (no "failed" language, no Retry) for payments whose
outcome is genuinely unknown past a 30s grace window, with a two-stage
poll backoff (2s → 15s) justified against the reconcile cron's ~10-minute
worst case.

## Deviation from the plan: `'refunded'` handling

The plan as written mapped `paymentStatus === 'refunded'` into the new
`'confirming'` bucket. Per explicit correction from the task issuer, this was
wrong in principle — `refunded` is a terminal, server-known outcome (money
was captured, then reversed), not an unknown one. Saying "still confirming
your payment" about a refund would be false.

**What I did:** `'refunded'` now routes to the existing `'failure'` branch,
alongside `'failed'`. Reasoning:
- It is terminal and known (same category as `'failed'`, not `'pending'`).
- The existing failure copy — "We couldn't confirm your payment. If money was
  deducted it will be refunded automatically. You can retry the payment for
  this order." — is truthful in effect for a refunded order: there is no
  outstanding charge (it was already reversed), so retrying is safe and does
  not carry the double-charge risk that motivated keeping `'confirming'`
  Retry-free. The tense ("will be refunded") is a pre-existing minor
  imprecision in the reused string, not something this plan's scope covers
  rewriting.
- I did not build any new refund-specific UI or copy — per the correction,
  this stays minimal. I added an inline code comment at the state-derivation
  site explaining why `'refunded'` is grouped with `'failed'` rather than
  `'confirming'`, and note here (as requested) that this was a deliberate
  choice, not an oversight.
- In practice `'refunded'` is close to impossible to observe on this screen
  immediately post-checkout (a full capture+reversal cycle before the
  customer even leaves the payment sheet), so this is a correctness edge
  case, not a commonly hit path.

No other deviations from the plan.

## Human verification steps for Task 3 (Android emulator required)

Build/run the customer app on an Android emulator (e.g. `Pixel_8_Pro`) with
the API pointed at your local backend, then confirm all five behaviours
below. Full detail and dev-only aids (temporarily shortening
`CONFIRM_GRACE_MS`, forcing a `pending` order via interrupted verify, forcing
`payment_status = 'failed'`/`'completed'` on a dev DB row) are in the plan's
Task 3 section — summarized here:

1. **Genuine failure (`paymentStatus === 'failed'`) — must be unchanged.**
   Trigger a Razorpay/Cashfree test-mode decline, or set
   `payment_status = 'failed'` on a dev order row. Confirm: "Payment not
   completed" title, Retry button present, tapping Retry actually re-opens
   the gateway sheet for the same order.

2. **Confirming (unresolved, past grace) — the new state.** Get a real order
   stuck in `pending` (interrupt the client verify call after a real test
   payment — airplane mode or force-quit right after the gateway sheet
   closes and before `/v1/payments/order/:id/verify` returns — no webhook
   configured locally means it stays `pending` server-side). Wait past grace
   (or shorten `CONFIRM_GRACE_MS` locally, e.g. to `3_000`, then revert the
   literal to `30_000` before handing off). Confirm:
   - Title/body never contain the word "failed" anywhere on screen.
   - No Retry button renders anywhere — visually confirm only two buttons
     ("View order", "My orders"), and/or `adb shell input tap` across the
     old Retry CTA position to confirm nothing responds there.
   - "View order" navigates to `/order/<id>`.
   - "My orders" navigates to `/(tabs)/orders`.

3. **Late-settle-still-wins.** While sitting on the `'confirming'` screen
   from step 2, flip that same dev order's `payment_status` to `'completed'`
   (DB write or a manual verify call) without navigating away. Confirm the
   screen flips to `'success'` on its own within one poll interval — ≤15s if
   already in the slow-poll window, or ≤ fast-interval + remaining grace if
   still in the fast window with a shortened `CONFIRM_GRACE_MS`. No
   navigation should be required to see the flip.

4. **No-orderId edge case still terminates.** Navigate directly to
   `/payment/result` with no query params (no resolvable `order_id`, no
   `error` param). Confirm it still reaches `'failure'` after the grace
   window elapses — it must not hang on `'confirming'` or `'checking'`
   forever, and must not claim to be "confirming" a payment that has no
   order to check.

5. **Refunded routes to failure, not confirming (this session's deviation —
   verify if you can force it).** If you can set
   `payment_status = 'refunded'` on a dev order row (near-impossible to hit
   naturally on this screen immediately post-checkout, so DB-forcing is the
   only practical way), confirm the screen shows the `'failure'` branch
   ("Payment not completed", Retry present) rather than `'confirming'`. This
   is a low-priority check given how rarely it's reachable in practice, but
   worth a quick DB-forced pass if time allows.

Before handing off for any further commits: revert every temporary aid
(`CONFIRM_GRACE_MS` back to `30_000`, no dev order rows left in a state that
would confuse later testing).
