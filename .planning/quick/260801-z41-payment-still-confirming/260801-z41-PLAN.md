# Quick Task 260801-z41: Stop telling customers a captured payment "failed"

Closes tesserix/Home-Chef-App#887.

## Goal

`apps/mobile-customer/app/payment/result.tsx` currently collapses two different
non-success outcomes into one `'failure'` state after a 25s grace window: a
server-confirmed decline, AND a payment whose outcome we genuinely don't know
yet (verify lost, no webhook configured, reconcile cron can take up to ~10
minutes to settle it — see `apps/api/services/order_payment_reconcile_cron.go`).
Both get the same "Payment not completed... You can retry the payment" copy
and CTA. Retrying a captured order is how a customer gets charged twice.

Split the two outcomes. A server-authoritative decline still shows failure +
Retry, unchanged. An unresolved/pending payment gets a new, honest
`'confirming'` state: no "failed" language, no Retry, and a poll strategy that
doesn't give up before the reconcile cron's worst case.

## Design decisions locked by this plan

**State shape.** Add a fourth state to the union:
`'checking' | 'confirming' | 'success' | 'failure'`. `'checking'` keeps its
current meaning (within the fast-poll grace window, spinner only). New
`'confirming'` is "past grace, still `pending`/`refunded`/undefined, no
server-authoritative verdict yet."

**Failure vs. confirming split.** A result counts as genuine, server-reported
`'failure'` only if:
- `paymentStatus === 'failed'` (server says so), OR
- `!orderId && Boolean(params.error)` (gateway errored before any order
  existed — nothing was ever charged), OR
- `!orderId && pastGrace` with no error either — there is no order to poll or
  link to, so there is nothing left to "confirm." This preserves the original
  purpose of the grace timer for the no-order edge case (must still
  terminate, not spin or claim to be confirming something that doesn't
  exist).

Everything else that is still not `'completed'` once `pastGrace` is true (i.e.
a real `orderId` whose `paymentStatus` is `pending`/`refunded`/`undefined`)
becomes `'confirming'`, not `'failure'`. `paymentStatus === 'completed'` is
still checked first and always wins, at any point — a late settle flips
`'confirming'` straight to `'success'`.

**Polling strategy — two-stage, justified against the reconcile numbers.**
- 0–30s (`'checking'`): poll every 2000ms — unchanged fast cadence, this is
  the window where the synchronous verify or a live webhook would normally
  land.
- After 30s (`'confirming'`): back off to 15000ms. Reasoning: the reconcile
  cron's worst case is ~10 minutes, so holding a 2s poll open that whole time
  would be ~300 requests and meaningfully draining on battery/radio for
  something the customer is just glancing at. 15s cadence is ~40 requests
  over the worst-case 10-minute window — still surfaces a settle within
  15s of it happening, and only runs while the screen is mounted AND the app
  is foregrounded (see the `focusManager` note above — background pauses it
  entirely). No hard upper stop is needed: `useOrder`'s own fallback logic
  already drops out of the `pollUntilPaid` branch the instant `paymentStatus`
  stops being `'pending'`.
- The grace boundary moves from 25s to 30s. This is not a meaningful change to
  the fast path (verify/webhook land in seconds either way) — it just gives
  the tight 2s poll a slightly rounder window before the tone/cadence switch.

**Copy for `'confirming'` (no "failed", no raw status/error strings, matches
the plain/calm voice of the existing success/failure copy in this file):**
- Title: "Still confirming your payment"
- Body: "This can take a few minutes. We'll update your order automatically
  the moment it's confirmed — there's no need to retry."
- Primary CTA: "View order" → `handleViewOrder` (same as the success branch —
  most likely outcome is the payment did go through).
- Secondary CTA: "My orders" → `handleGoToOrders` (same as the success
  branch).
- No Retry affordance anywhere in this branch.
- Visual: reuse the existing `pendingCircle` style + `ActivityIndicator` (same
  language as `'checking'` — still in progress, not resolved, not alarming).
  No new color token; per the design system's "one accent, used sparingly"
  rule this stays in the same coral/pending family already used for
  `'checking'`.

## must_haves

**truths:**
- A customer whose payment was genuinely declined by the server still sees
  "Payment not completed" and can retry — unchanged from today.
- A customer whose payment outcome is still unknown (pending past grace) never
  sees the word "failed" and never sees a Retry button.
- That same customer's primary path is "View order" / "My orders" — they can
  go watch the order resolve instead of being stuck on this screen or risking
  a double charge.
- A payment that settles late (webhook lag, reconcile cron) flips
  `'confirming'` → `'success'` automatically, without navigation, at any
  point — even minutes later.
- A result screen reached with no resolvable order id and no error param still
  terminates (does not spin or falsely claim to be "confirming" something
  that doesn't exist).

**artifacts:**
- `apps/mobile-customer/hooks/useOrderHistory.ts` — `useOrder()` accepts
  `pollIntervalMs`, default behavior for existing callers unchanged.
- `apps/mobile-customer/app/payment/result.tsx` — `state` is
  `'checking' | 'confirming' | 'success' | 'failure'`; new `'confirming'`
  render branch with the specified copy and no Retry.

**key_links:**
- `apps/mobile-customer/app/payment/result.tsx` → `useOrder(orderId, {
  pollUntilPaid: true, pollIntervalMs })` — the poll cadence the whole fix
  depends on.
- `apps/mobile-customer/hooks/useOrderHistory.ts` `refetchInterval` closure →
  `apps/api/services/order_payment_reconcile_cron.go`'s ~10-minute worst case
  — the number the backoff is justified against.
