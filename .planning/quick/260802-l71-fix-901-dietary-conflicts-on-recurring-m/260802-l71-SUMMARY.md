# Fix #901: Dietary Conflict Warnings on Recurring/Tiffin Surfaces Summary

**Allergen badges + calm dietary-conflict warnings now appear on all four recurring-meal surfaces a subscriber sees (weekly-menu preview, booked plan day list, tiffin subscribe screen, and book-meal-plan) — reusing the existing `#41` matcher/hook, no new dependency, no API change.**

## Performance

- **Duration:** ~10 min (4 commits, 15:27–15:33 local time)
- **Tasks:** 3 planned tasks + 1 scope-addition task, all completed
- **Files modified:** 8

## Accomplishments

- `WeeklyMenuItem` (client type) now carries `dietaryTags`/`allergens`, and `MealPlanDay` now carries `weeklyMenuItemId` — both fields the server already sent (#41) but the client silently discarded.
- `WeeklyMenuDishCard` (the chef-detail "This week's menu" preview card) renders allergen badges + a conflict warning via `useDietaryConflicts`, matching `MenuItemCard`'s existing visual tone, wrapped for its narrower 150px width.
- `MealPlanDayList` (shared by the plan-detail screen and the "Show my plan" sheet) shows a per-day conflict warning, resolving each day's dish via `weeklyMenuItemId` against the chef's weekly menu — falling back to the day's own `variant` for a veg/non-veg clash when the dish can't be resolved, so it never silently shows nothing.
- The daily-tiffin subscribe screen (`meal-subscription/[chefId].tsx`) shows a single calm, non-blocking banner when the chef's weekly-menu dishes for the selected slots/days/variant clash with the customer's profile — Subscribe stays enabled.
- **Scope addition:** `book-meal-plan.tsx` — the screen where a customer actually commits money to a week of meals, and the only fulfilment path currently working in production (`meal_subscriptions` is stuck at `trialing`) — got the identical calm, non-blocking banner treatment. Required extending the client `DailyMenuItem` type with `dietaryTags`/`allergens` (server already sends them; same silent-drop gap as `WeeklyMenuItem`).

## Decisions Made

- **Scope addition accepted and implemented:** `book-meal-plan.tsx` was deliberately added beyond the plan's written scope per explicit instruction — it is the primary money-commit path today, and a conflict warning that covers subscribe but not book would leave the working purchase flow silent. Assessed as a modest, self-contained addition (the server already sends the needed fields on `DailyMenuItem`; the screen already tracks full cell data at selection time), so implemented rather than deferred.
- book-meal-plan's conflict check runs against the customer's actual picks (`selected`, built from `Object.values(selection)`), carrying `dietaryTags`/`allergens` through from the cell at `toggle()` time — this avoids re-deriving cell data via a lookup and stays accurate as the selection changes.
- Local `tsc` baseline measured **0** errors, not the documented 1 (`lib/payment.ts`). Verified this is pre-existing (not caused by any of this plan's edits) by targeted `git checkout --` + `git apply` round-trips on just the touched files before committing Task 1 — matching the CLAUDE.md guidance that local `.expo/types` drift is stale and shouldn't be chased. All four commits kept the count at 0 (no new errors introduced).
